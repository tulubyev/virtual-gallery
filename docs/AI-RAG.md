# RAG: вопросы по документам (этап 1)

Что сделано по плану `docs/AI-RAG-RESEARCH.md`, разд. 8, этап 1. Исследование остаётся источником обоснований; здесь — как работает код.

## Как это устроено

```
PDF (сотрудник) ──► Express /api/ai/process-pdf ──► ядро /api/v1/pdfs/upload ──► очередь (ai_jobs)
                                                                                    │
      страницы → фрагменты (≈1000 зн., по страницам, перекрытие ≤150) → эмбеддинги (bge-m3 через routerai)
                                                                                    ▼
                       PostgreSQL: kb_documents + kb_chunks (текст, страница, доступ, tsvector 'russian')
                       Qdrant: pdf_chunks (вектор + document_id, chunk_index, access)

вопрос ──► Express /api/ai/rag-query ──► ядро /api/v1/rag/query
              (роль из сессии → access, mode)      │
                       поиск по смыслу (Qdrant) + по словам (PostgreSQL, морфология) → слияние RRF → top-20
                       из PostgreSQL перечитываются текст, страница, название и ПРАВА → 8 лучших + соседние фрагменты → в модель
                       ответ модели по схеме {insufficient_evidence, blocks[kind, source_ids, quote]}
                       проверка → (одна попытка исправления) → ответ / отказ
```

- **Права.** У каждого документа `access`: `public` (видят все, в том числе гости) или `staff` (сотрудники, кураторы, администраторы).
  По умолчанию — `staff`: опубликовать можно только сознательно, и только куратору или администратору. Уровень спрашивающего определяет
  Express по сессии (`req.user`), а не тело запроса; ядро повторно проверяет `access` по PostgreSQL, что бы ни вернул Qdrant.
- **Поиск.** Смысловой и лексический поиск работают независимо; если один отказал (нет эмбеддингов в `LLM_MODE=ru-only`, недоступен Qdrant),
  ответ строится по второму, а в ответе `retrieval.degraded` и пометка в интерфейсе. Лексический — `to_tsquery('russian', …)` с «или» между словами
  (`ts_rank_cd`), поэтому «картины» находит «картина». Qdrant и клиент остаются на 1.9 (`client.search`), обновление не требуется.
- **Соседние фрагменты.** Ответ часто начинается сразу после места, где совпали слова вопроса (фрагмент режется по ~1000 знаков).
  `retrieval.expand_context` берёт 8 лучших находок (`context_limit`) и добавляет следующий фрагмент того же документа у каждой, предыдущий — у лучшей,
  пока контекст не дойдёт до 15 000 знаков (находки не отбрасываются никогда). Следующий берём у всех: на вопросах набора ответ лежал в следующем
  фрагменте у находки не только первой, но и четвёртой по счёту, а предыдущий фрагмент ответа не добавил ни разу. В контексте фрагменты одного документа
  идут подряд в порядке текста. Права проверяются заново: служебный сосед не попадёт в публичный ответ.
- **Поиск по написанию.** Слово вопроса, которого нет в базе («Занабазар»), дополняется похожими по триграммам леммами из `kb_terms`
  («дзанабадзар»): `pg_trgm`, порог сходства 0,38, не более двух слов на одно, основа не короче 6 знаков. Формы того же слова (общее
  начало из 4 букв) не подставляются — их находит морфология. Таблицу наполняет `knowledge_base.replace_document`, начальное заполнение —
  миграция `008_kb_terms_trigram.sql`. **Если расширение `pg_trgm` не создалось** (у роли нет прав — миграция при этом проходит, в журнале
  `pg_trgm не создано`), выполните один раз от суперпользователя `CREATE EXTENSION pg_trgm;` в базе ядра и затем
  `CREATE INDEX IF NOT EXISTS idx_kb_terms_trgm ON kb_terms USING GIN (term gin_trgm_ops);`. Без расширения и без таблицы поиск идёт как раньше
  (в журнале одна строка `Поиск по написанию недоступен`).
- **Проверка ответа** (`services/rag_answer.py`, детерминированная): номера источников существуют; у утверждений есть источник; цитата —
  дословная подстрока источника (после нормализации пробелов, дефисов, кавычек, ё); числа и годы из текста есть в процитированных источниках;
  имена собственные (слова с заглавной не в начале предложения) встречаются в источниках по основе слова; нет суждений о подлинности и «гарантированной цены».
  В публичном режиме — не более 3 цитат по 300 знаков и без блоков-выводов. Нарушение → один повтор с перечнем замечаний → «ответ не подтверждён» с показом найденных мест.
- **Отказ.** Нет найденных фрагментов → отказ без вызова модели. Модель вернула `insufficient_evidence` → отказ. Порога по косинусу нет
  (число из прежней версии под другую модель не годилось); порог, если понадобится, подбирается на золотом наборе.
- **Журнал.** `rag_queries`: вопрос, ответ, источники, исход (`answered | insufficient_evidence | no_sources | citations_failed`), уровень доступа, время.

## Что нужно знать при эксплуатации

- Загрузка — только сотрудники (`staff`, `curator`, `admin`), удаление — куратор и администратор (`accessPolicy.ts`). Файл до обработки лежит в томе `ai-spool`
  (`/var/spool/vg`), после успешной обработки удаляется, неудавшиеся чистятся через сутки.
- Повторная загрузка с тем же `documentId` целиком заменяет фрагменты документа (в PostgreSQL — одной транзакцией, в Qdrant — удалением и записью).
- Документы, проиндексированные прежним кодом, не видны: у их точек нет `access` и текста в `kb_chunks`. Загрузите их заново.
- Каждый вопрос — один-два вызова модели `rag_answer` (выбирается во вкладке «Модели ИИ») и один вызов эмбеддингов; лимиты — `aiBudget.ts`.
- Распознавание сканов (OCR) включается, только если во всём PDF меньше 1000 знаков текста; смешанные PDF (часть страниц — сканы) пока не поддержаны.

## Оценка качества

Золотой набор, формат и запуск — `ai-ml-service/eval/README.md`, код — `ai-ml-service/tools/rag_eval.py` (метрики поиска, доля отказов,
перепроверка цитат, парный бутстрэп для сравнения прогонов).

Hit@5 и Recall считаются по страницам, поэтому завышают: страница найдена, а фрагмент с ответом в контекст не попал (так было с вопросом о сплаве
статуэтки). «Ответ в тексте@5» и «Ответ в контексте» ищут в самих фрагментах дословную фразу-ответ (`phrase` в разметке) — смотрите на них.
Сплиты `test` и `fresh` использованы для разбора ошибок, поэтому независимыми они больше не являются: это справка, а не оценка на новых данных.

### Итог этапа 1 (24.10.2026)

Модель ответа `google/gemini-3.5-flash-lite` (работает из РФ, выбирается во вкладке «Модели ИИ»), корпус из 10 открытых PDF (3367 фрагментов), набор
`ai-ml-service/eval/siberia-art.golden.jsonl` (42 вопроса, из них 31 с ответом), код на коммите `1f23c3e1` и позже. Три прогона `dev` подряд, по одному `test` и `fresh`:

| Сплит | Вопросов (с ответом) | Ложный отказ | Нарушения цитат | Отказ на неотвечаемых и провокациях | Ответ в контексте | P95, с |
|---|---|---|---|---|---|---|
| dev (3 прогона) | 19 (14) | 0 / 0 / 0 % | 0 | 100 % | 1,00 | 4,0–4,5 |
| test | 11 (7) | 0 % | 0 | 100 % | 1,00 | 6,9 |
| fresh | 12 (10) | 0 % | 0 | 100 % | 0,90 | 3,3 |

Цели плана (ложных отказов не больше 10 %, нарушений цитат 0, отказ на неотвечаемых не меньше 90 %, P95 не больше 6 с) выполнены, кроме P95 на `test`
(6,9 с на 11 вопросах — по сути самый долгий вопрос). Путь к этим цифрам: ложные отказы 7–21 % (разорванные слова и номера сносок после замены PyMuPDF, #44), затем 28,6 % на `test`
(ответ в соседнем фрагменте и другое написание имени, #45, #46), затем опечатка модели в цитате, которую повторная попытка с названием расходящегося знака исправляет (#47).

Известные ограничения:
- **Ранжирование.** На `fresh` вопрос q-101 («Сколько изображений Майтреи подобрал Ольденбург…») не получает нужный фрагмент в первые 5 (Hit@5 0,90), модель отвечает по другому месту. Лечится реранкером (этап 2).
- **Размер и авторство набора.** 42 вопроса написал агент, не куратор; на таком объёме интервалы широкие (на 10 вопросах «0 %» значит «не больше двух из десяти»). Независимую оценку даст набор куратора на 100–150 вопросов с `split`, не попадавшим в разбор ошибок.
- **Один тип модели.** Цифры только для Gemini Flash Lite; смена модели требует нового прогона (`--model`, не меньше двух прогонов на `dev`: ответ модели недетерминирован).
- **Лицензии корпуса не установлены**, поэтому документы остаются `staff`; публичный режим на этих данных не включался.
- **Стоимость.** Контекст стал шире (около 13 фрагментов, до 15 000 знаков вместо 8 фрагментов): токенов на вопрос больше. Расход смотреть в журнале `rag_queries`/счёте routerai после недели работы.

## Чтение PDF

Текст страниц читает **pypdfium2** (PDFium; Apache-2.0/BSD, `pdf_service.extract_text`), страницы для OCR он же рисует в изображения (`render_pages`, 200 dpi), а распознаёт Tesseract. PyMuPDF (AGPL-3.0, обязывает открыть код всего сервиса при работе через сеть) и poppler из зависимостей убраны.
Сравнение на корпусе из 10 PDF (лексический поиск, 30 вопросов): Hit@5 и Recall@20 те же, что у PyMuPDF (0,71 и 0,91), MRR@10 0,48 против 0,46, загрузка быстрее (5 с против 8 с); у pypdf (0,57 и 0,87) и pdfminer.six (0,67 и 0,83) качество хуже.
Документы, загруженные до замены, переиндексировать не обязательно, но фрагменты у них нарезаны по тексту PyMuPDF; при желании загрузите их заново.

## Тестовый корпус для оценки

`ai-ml-service/eval/corpus/manifest.tsv` — 10 открытых PDF по искусству Сибири, Бурятии и Монголии (сайты Кунсткамеры и РЭМ): id, SHA-256, адрес, название.
Сами файлы в git не лежат. Загрузка в работающее приложение (повторный запуск заменяет документы с теми же id, так корпус перезагружают после смены нарезки):

```bash
VG_EMAIL=<почта сотрудника> scripts/rag-load-corpus.sh [doc-01 doc-05 …]   # пароль спросит в терминале
```

Скрипт скачивает файлы, сверяет SHA-256 (номера страниц в золотом наборе относятся именно к этим файлам), загружает через `/api/ai/process-pdf` с доступом `staff` и ждёт появления документов в базе знаний.
Лицензии не установлены (`license` = «не установлено»): публиковать документы для гостей нельзя.
