## 1. Краткое резюме

**Состояние.** Раздел «Аукцион» сейчас — витрина с таблицами `auctions`, `auction_lots`, `bids` и одним работающим API ставки. Это не аукцион. Нет: шага ставки, антиснайпинга, резервной цены (поле пишется, но нигде не читается), покупки «сразу», закрытия торгов, определения победителя, оплаты, допуска участников, реального времени. Ни `auctions.status`, ни `auction_lots.status` не меняются нигде в коде после создания (в `auctions.ts` всего два `UPDATE`: `bids.is_winning` на стр. 326 и `current_bid`/`highest_bidder_id` лота на стр. 332).

**Главные находки аудита**

1. **Кнопка «Сделать ставку» на странице `/auction` не работает.** Клиент шлёт `POST /api/auctions/lots/:id/bid` (`AuctionPage.tsx:169`), такого маршрута в роутере нет (есть только `POST /api/auctions/bids`, `auctions.ts:299`). Ошибка проглатывается без сообщения (`AuctionPage.tsx:174-190`). Работает только устаревшая HTML-страница `auction.html:453`.
2. **Резервная цена утекает в публичный API** (`al.*` в `auctions.ts:202` и `:229`, доступ публичный — `accessPolicy.ts:70`). Заодно публично отдаются `user_id` и логины участников (`:249-251`, `:205`, `:80-85`). Маскировка логина есть только в браузере (`AuctionPage.tsx:51-54`).
3. **Ставки не защищены от гонок и не проверяют стартовую цену** (`auctions.ts:309-334`): три отдельных запроса без транзакции и блокировки; первая ставка может быть 1 ₽ при старте 50 000 ₽.
4. **«Допуск» участника — это выпадающий список при регистрации** (`auth.ts:70`, `RegisterPage.tsx:122`). Любой может назначить себе роль `auction_participant` и ставить без проверки личности и без залога.
5. **Фейковые данные в кабинете участника:** баланс «2 450 000 ₽» зашит в разметку (`AuctionParticipantPanel.tsx:276`), при отсутствии пользователя подставляется «bidder@gallery.com, id=1» (`:50-51`). Это противоречит правилу проекта «выдуманных значений быть не должно» (`CLAUDE.md`, раздел «Дашборды»).
6. **Socket.IO в проекте есть, но к аукционам не подключён и в prod не запускается** (подробнее — 2.6).
7. **SEO:** публичных адресов у аукционов и лотов нет вообще (всё на одной странице `/auction`, лоты раскрываются кнопкой), `sitemap.xml` и `robots.txt` отсутствуют, а любой неизвестный адрес отдаёт `index.html` со статусом 200 (`server.js:94-101`).

**Пять самых важных решений**

| № | Решение | Почему сейчас |
|---|---|---|
| 1 | **Правовая рамка:** кто организатор торгов (юрлицо/ИП), работаем ли «по ст. 447-448 ГК» (торги с публичным извещением, протоколом и задатком) или по публичной оферте с Правилами аукциона как посредник (комиссионер/агент) `[Ю]` | От этого зависят задаток, сроки извещения (в ГК — не позднее 30 дней до торгов `[И-1]`), чеки, договоры с владельцами работ, налоги |
| 2 | **Деньги:** задаток/холд через эквайринг (ЮKassa, CloudPayments) или ручной задаток по реквизитам на первом этапе | Холд по картам держится до 7 дней `[И-6][И-7]`, а аукцион может идти дольше; СБП, судя по косвенным данным, одностадийный `[И-8]` `[Н]` |
| 3 | **Новое ядро торгов:** транзакционная ставка (`SELECT … FOR UPDATE`), шаг, резерв, антиснайпинг, воркер закрытия, протокол | Без этого выпускать публично нельзя: гонки, утечка резерва, нет победителя |
| 4 | **Допуск участников как отдельный процесс:** заявка → проверка (KYC) → решение → согласия (152-ФЗ) → правила/оферта; роль не выбирается при регистрации | Закрывает фиктивные ставки, неоплату, ПДн |
| 5 | **SEO через серверную выдачу HTML для публичных страниц** `/auctions/:slug`, `/lots/:slug` (лёгкий SSR в существующем Express + JSON-LD + sitemap), без переезда на Next.js | Яндекс сам рекомендует SSR/пререндер, рендер JS в Вебмастере — бета `[И-9]`; сейчас индексировать нечего |

**Рекомендуемый порядок:** сначала этап 0 (исправления, 1-2 недели), затем MVP без онлайн-платежей (этап 1), потом деньги и чеки (этап 2), потом рост и AI (этап 3). План и таблица — раздел 4.

## 2. Аудит кода

### 2.1. Сущности и статусы

Таблицы создаются на лету при первом запросе и при импорте роутера (`CREATE TABLE IF NOT EXISTS`, `auctions.ts:8-52`). Миграций нет; индексов, внешних ключей и `CHECK` в этих DDL нет (в `enhanced_schema.sql:171-210` и `migration.sql:128-160` ключи и индексы есть, но какая версия в боевой БД — `[Н]`, БД не смотрели).

| Сущность | Поля | Замечания |
|---|---|---|
| `auctions` (`:11-23`) | `auction_id`, `name`, `description`, `organizer_id`, `gallery_id`, `start_datetime`, `end_datetime`, `status`, `created_at`, `updated_at` | `status` — свободная строка, по умолчанию `'scheduled'`; по комментарию в `enhanced_schema.sql:180` допустимы `scheduled/active/ended`. Время — `TIMESTAMP` без часового пояса. Окончание одно на весь аукцион, не на лот |
| `auction_lots` (`:25-38`) | `lot_id`, `auction_id`, `artwork_id`, `starting_price`, `reserve_price`, `buy_now_price`, `current_bid`, `highest_bidder_id`, `status`, … | `status` по умолчанию `'available'`; в схеме `enhanced_schema.sql:196` — `available/sold/withdrawn`. Цены `DECIMAL(10,2)` — потолок 99 999 999,99 ₽, для дорогих лотов мало. Нет: оценки (эстимейта), шага, описания лота, провенанса, условий, номера лота, владельца-консигнатора, комиссии |
| `bids` (`:40-48`) | `bid_id`, `lot_id`, `user_id`, `amount`, `timestamp`, `is_winning` | Нет IP/устройства, типа ставки (ручная, автоставка, buy-now), идентификатора запроса (идемпотентность) |
| Роль участника | `users.role = 'auction_participant'` (`auth.ts:70`, `users.ts:7`) | Нет таблицы заявок, статусов допуска, договоров, ПДн-согласий, залогов, платежей |
| Нет вообще | оплаты, инвойсы, задатки, доставка, протокол торгов, подписки/наблюдение, автоставки | |

**Статусы.** Реально задаются только значения по умолчанию. `UPDATE auctions` в проекте нет (поиск по репозиторию), `UPDATE auction_lots` — единственный, на `auctions.ts:332` (`current_bid`, `highest_bidder_id`). Следовательно:
- аукцион всегда `scheduled`, лот всегда `available`, `sold` и `ended` недостижимы;
- «активность» вычисляется из дат: `auctions.ts:60`, `:86`, `:131`, `:143`, `:317-318`; а фильтры списка — по колонке `status` (`:181`). Эти два способа расходятся (см. 2.3, п. 9).

### Б.1. Создание аукциона и лотов

**Форматы.** Рекомендация — стартовать с одного формата и добавлять остальные позже.

| Формат | Суть | Подходит для проекта | Сложность |
|---|---|---|---|
| Английский (возрастающий) с таймером и продлением | Ставки только вверх, победитель — максимальная; окончание продлевается при поздних ставках | **Основной, этап 1.** По ГК РФ победителем аукциона признаётся предложивший наиболее высокую цену `[И-1]` | M |

| Онлайн с жёстким таймером без продления | Дешёвый вариант | Не рекомендуется: провоцирует снайпинг | — |

**Терминологическая ловушка `[Н][Ю]`.** В ГК РФ «открытый/закрытый аукцион» означают не «ставки видны/невидимы», а круг участников: в открытом участвует любое лицо, в закрытом — только приглашённые (формулировка «Аукционы и конкурсы могут быть открытыми и закрытыми» подтверждена выдачей `[И-1]`; смысл разграничения приведён по памяти и в сниппетах не раскрыт). «Sealed-bid» надо называть «аукцион с закрытыми ставками».

**Параметры лота (набор полей).**

| Группа | Поля |
|---|---|
| Идентификация | номер лота, `artwork_id`, owner/консигнатор, статус работы |
| Описание | название, автор, год, техника, размеры, состояние, подпись/маркировки, описание, фото, ссылка на 3D-зал |
| Провенанс и подлинность | история владения, выставки, публикации, экспертные заключения, каталог-резоне, свидетельства; поле «происхождение не подтверждено» `[О]` |
| Цены | стартовая цена, **эстимейт (нижняя/верхняя)**, резерв (скрытый), шаг (шкала), buy-now |
| Условия | комиссия покупателя, налоги/сборы, срок оплаты, срок вывоза, доставка, возвраты, право следования (кто платит) |
| Время | окно торгов, окно продления, максимальное число продлений |

**Антиснайпинг.** Типовой приём: ставка в последние N минут продлевает окончание лота. Пример реализации у стороннего сервиса: «если ставка поступит в последние 5 минут, время окончания продлевается на 5 минут, число продлений не ограничено» (доменный аукцион Dynadot — только как иллюстрация механики `[И-18]`, не как рекомендация параметров). Для арт-аукциона параметры (окно 2-5 минут, продление равно окну, потолок по общему времени) подбирать с аукционистом `[О]`. Окончание должно быть **на лот** (лоты закрываются поочерёдно с интервалом) или на аукцион целиком — это продуктовое решение (вопрос 9 в разделе 5).

**Шаг ставки.** Хранить шкалу «диапазон цены → шаг» в аукционе; сервер сам принимает только `текущая + шаг` или кратные. Конкретные значения шкалы — решение аукциониста `[О]`.

**Резерв.** Если резерв не достигнут — лот не продан («снят»/«не продан»), владельцу и участникам не раскрывается резерв; отдельно решить, показывать ли пометку «резерв достигнут» (практика рынка `[О]`). Резерв и скрытые параметры не отдавать из API (см. 2.3, п. 2).

**Что построить в интерфейсе.** Админ-форма «создать аукцион → добавить лоты из каталога `artworks` → проверка → публикация»; статус «черновик → опубликован → идут торги → завершён → закрыт»; предпросмотр публичной страницы лота. Сейчас этого интерфейса нет (2.2).

**Данные работы (`artworks`).** В схеме нет цены, владельца, провенанса, состояния (`artworks` в `schema.sql:46-63`; колонки `status/country/epoch` добавлены в боевой БД отдельно — `CLAUDE.md`). Нужна связка «работа → консигнатор (юрлицо/физлицо) → договор комиссии/поручения».

### Б.2. Проведение торгов

**Ставки в реальном времени.** Рекомендуемая схема (без новой инфраструктуры):

1. Ставка — `POST /api/auctions/lots/:id/bids` (идемпотентный ключ в заголовке), в транзакции `SELECT … FOR UPDATE` по лоту; сервер проверяет допуск, статус, время, шаг, резерв, лимит участника.
2. После `COMMIT` — событие Socket.IO в комнату `lot:<id>`: новая цена, ник-псевдоним лидера, время окончания (с продлением), число ставок.
3. Клиенты берут время от сервера (смещение часов), не от `Date.now()`.
4. Для надёжности — «подтверждённая» ставка возвращается в ответе HTTP; сокет только уведомляет. При обрыве клиент повторно запрашивает состояние.

Socket.IO есть в зависимостях, но не подключён (2.6). Для одного контейнера хватит in-process, для нескольких — Redis-адаптер и sticky-сессии `[И-17]`.

**Закрытие и победитель.** Воркер раз в секунду-пять находит лоты с `ends_at <= now()` и закрывает в транзакции: статус `sold` (если цена ≥ резерв) или `unsold`; фиксируется победитель, итоговая цена, формируется «протокол торгов». В ГК победитель и организатор подписывают протокол в день торгов, протокол имеет силу договора; уклонившийся возмещает убытки сверх размера обеспечения `[И-1]` `[Ю]` — для онлайн-аукциона это значит принятие правил при допуске и электронное подтверждение результата (ПЭП/кнопка + журнал) `[Ю]`.

**Оплата и передача.** Последовательность (после закрытия):

| Шаг | Срок (параметр в Правилах) | Что происходит |
|---|---|---|
| Уведомление победителя | сразу | письмо + кабинет + Telegram-бот (если выберете, см. Б.5) |
| Счёт / ссылка на оплату | сразу | цена + комиссия покупателя − зачтённый задаток |
| Оплата | например 3-7 дней `[О]` | карта/СБП/счёт на юрлицо |
| Чек | в момент расчёта | 54-ФЗ (Б.3) |
| Передача | после оплаты | самовывоз (в зале/мастерской), доставка, акт приёма-передачи; вывоз за границу — отдельная разрешительная процедура (см. вопрос 7 в разделе 5) |
| Закрытие | после подтверждения | выплата продавцу за вычетом комиссии, отчёт, право следования |

**Что делать при неоплате.** Набор мер должен быть прописан в Правилах и в соглашении о задатке `[Ю]`:
1. Напоминание и льготный срок.
2. Удержание задатка у победителя (в ГК: при вине давшей задаток стороны он остаётся у получившей `[И-2]`).
3. Предложение лота второму лидеру по его последней ставке (если это предусмотрено правилами) `[О]`.
4. Повторные торги.
5. Блокировка участника, внесение в внутренний список.
Если задатка нет (этап 1), единственное средство — убытки по протоколу; на практике это слабая защита, поэтому для лотов дороже порога допуск без задатка не рекомендуется `[О]`.

**История ставок.** Публично — «таймлайн» без личных данных (псевдонимы); полная история — организатору. Хранить неизменяемым журналом (append-only), с сервером-временем и идентификатором запроса.

**СБП.** Косвенные сведения: в документации Яндекс Пэй оплата через СБП — одностадийная, средства списываются сразу `[И-8]`; поддержка двухстадийного платежа через СБП у ЮKassa/CloudPayments **не найдена** `[Н]` — проверить у провайдера. Для задатка СБП пригоден как «списание + возврат».

**Чеки и 54-ФЗ.** Общая схема из выдачи: при получении предоплаты пробивается чек, при передаче предмета расчёта — второй чек; в чеке указывается признак способа расчёта (аванс/полный расчёт и т.д.) `[И-15]`. Как квалифицировать именно задаток в чеке — **не подтверждено**, зависит от договора `[Ю][Н]`. Для маркетплейс-модели ЮKassa описывает отдельные чеки на вознаграждение площадки при двухстадийном платеже (чек при `waiting_for_capture`, при частичном списании — возврат и новый приход) `[И-6]`; чеки продавцов — на их стороне `[Н]`. Задача для бухгалтера: кто продавец в чеке — организатор (комиссионер) или владелец работы `[Ю]`.

**Насколько SPA мешает индексации.**

- Яндекс: в Вебмастере есть настройка «Рендеринг страниц JavaScript» (бета); по умолчанию «на усмотрение робота»; в справке указано: если на сайте реализован SSR или пререндеринг, рендеринг надо запретить; при выполнении JS робот может давать дополнительную нагрузку `[И-9]`. Отраслевые материалы (Kokoc и др.) приводят эксперименты, где скрипты обрабатываются нестабильно `[И-9]`, но это вторичные источники `[Н]`. Вывод: опираться на рендеринг робота нельзя, надёжный путь — отдавать готовый HTML.
- Google: «динамический рендеринг» (подмена HTML для ботов) больше не рекомендуется; официальные альтернативы — SSR и статическая генерация `[И-10]`. Робот Google рендерит JS, но с задержкой; для динамичных лотов рискованно `[Н]`.
- Для публичных аукционов и лотов (контент меняется: цены, статусы) подходят: SSR на запрос или генерация страниц при изменении данных (ISR-подобно); чистый пререндер на сборке не подходит — лоты создаются после сборки `[И-9]`.

**Варианты решения и оценка трудоёмкости.**

| Вариант | Суть | Трудоёмкость | Плюсы | Минусы |
|---|---|---|---|---|
| **A. Лёгкий SSR/«шаблонные» публичные страницы в Express (рекомендуется)** | Для маршрутов `/auctions`, `/auctions/:slug`, `/lots/:slug`, `/artists/:slug` сервер сам формирует HTML (шаблонизатор или `react-dom/server` для небольших компонентов): `<title>`, `description`, canonical, OG, JSON-LD, основной текст, изображения, ссылки; в конец вставляет скрипт SPA, который «подхватывает» страницу (или не гидрируется, а динамика — отдельным островком) | **M** (≈ 8-15 чел.-дней: маршруты, шаблоны, slug, sitemap, кэш, тесты) | Остаётся текущий стек и деплой; быстрая отдача; контроль над кэшем | Два способа рендера лотов — дублирование разметки; нужна дисциплина |
| B. SSR для всего SPA на Vite (`vite-ssr`/`vite build --ssr`) | Серверный рендер тех же React-компонентов | **L** (≈ 15-30 чел.-дней; зависят от использования `window`, `localStorage`, R3F/Three.js в компонентах) | Один код для сервера и клиента | Много компонентов используют браузерные API (3D-галерея, `localStorage` в кабинетах: `AuctionParticipantPanel.tsx:49`) — потребуются защитные проверки |
| C. Миграция публичной части на Next.js/Remix/Astro | Отдельное приложение для публичных страниц | **L-XL** | Лучшая экосистема SEO | Два фронтенда, новый деплой, переезд маршрутов |
| D. Предварительный рендер сервисом (prerender.io/Rendertron) | Подмена HTML для ботов | **S-M** | Минимум правок | Для Google это «dynamic rendering» — не рекомендуется `[И-10]`; вынос данных за пределы РФ — вопрос локализации `[Ю]` |
| E. Статические страницы-генерация при публикации/закрытии лота | Воркер пишет `.html` в каталог, Express раздаёт | **M** | Быстро, дёшево; идеально для архива завершённых торгов | Нужна перегенерация при изменении |

### Б.7. Формирование цены произведения

**Термины (общеотраслевое понимание, `[О]`).**

| Термин | Что это | Кто задаёт | Видимость |
|---|---|---|---|
| Стартовая цена | С чего начинаются ставки | Аукционист по согласованию с владельцем | Публично |
| Эстимейт (оценка) | Вилка «от-до» ожидаемой цены молотка | Эксперт аукциона | Публично (в каталоге) |
| Резерв | Минимум, ниже которого владелец не продаёт | Владелец и аукцион | Скрыт; обычно не выше нижней оценки |
| Молоток | Цена последней ставки | Рынок | Публично после торгов |
| Комиссия покупателя | Надбавка к молотку, платит покупатель | Аукцион | Публично в условиях |
| Комиссия продавца | Удержание из выручки владельца | Договор с консигнатором | Не публично |

**Методы оценки.**

| Метод | Суть | Данные | Применение |
|---|---|---|---|
| Сравнительный (по результатам торгов) | Берутся проданные аналоги: автор, техника, размер, период, состояние, происхождение; поправки | Результаты аукционов (по автору/периоду) | Базовый метод для эстимейта |
| Экспертная оценка | Мнение специалиста: качество, редкость, тематика, провенанс, спрос | Опыт эксперта, архивы | Обязателен для высоких лотов и неликвидных авторов |
| Индексы рынка | Динамика цен по сегменту: повторные продажи (repeat sales) и гедонические индексы | Базы продаж (Artprice, Artnet, российские — ARTinvestment и др.) | Поправка «год к году», контекст |
| Гедоническая регрессия | Цена как функция признаков (автор, размер, техника, год, подпись…) | Большая выборка продаж | Автоматическая «прикидка», основа AI-подсказки |

Из выдачи: два основных подхода к индексам — повторные продажи и гедонический; в гедонической модели цены регрессируются на характеристики (размер, автор, тематика) и остатки используются для индекса; у повторных продаж — выборочное смещение (видны только перепродававшиеся работы); у гедонических — неверная форма модели и нестабильность коэффициентов `[И-13]`. В одной работе по эстампам характеристики (размер и т.п.) объясняли порядка 68% молотковых цен `[И-13]`, в крупной выборке (более миллиона сделок) реальная доходность искусства 1957-2007 гг. оценена в 3,97% годовых в долларах `[И-13]`. Эти цифры — лишь иллюстрация методов; для России применимость не проверялась.

**Стартовая цена, эстимейт, резерв: рекомендации по политике (`[О]`, решает аукционист).**
- Стартовая цена — привлекательная точка входа, существенно ниже нижней оценки (задаёт ожидание и «вовлекает» участников).
- Эстимейт — вилка по сравнительному методу, показываемая в каталоге.
- Резерв — не выше нижней оценки; договором с владельцем фиксируется порядок снижения при отсутствии продажи.
- Для лотов без резерва — явная пометка «без резерва» (повышает интерес).

**Комиссии, налоги, право следования.**

| Тема | Что известно | Статус |
|---|---|---|
| Комиссия покупателя / продавца | Размеры у российских домов в выдаче не найдены | `[Н]` — собрать с сайтов конкурентов (раздел 6); зависит от вопроса 2 |
| НДС, НДФЛ, налог на прибыль | Поиск не дал российских разъяснений (получены материалы по Украине — не применимы). Применяются нормы НК РФ для комиссионера, налоговый режим организатора; для физлиц-продавцов — НДФЛ, особенности для художников-авторов | `[Н][Ю]` — вопрос бухгалтеру/налоговому консультанту |
| **Право следования (ст. 1293 ГК)** | Автор оригинала произведения изобразительного искусства имеет право на процентные отчисления от цены каждой последующей перепродажи, если в ней участвует юрлицо или ИП (аукционный дом, галерея); платит продавец `[И-3]`. Размер, условия и порядок выплаты — по актам Правительства: постановление № 285 от 19.04.2008 (в редакции с изм. 2018 г.), размер — по приложению `[И-3]`. Поправки в ст. 1293 вступили в силу 01.06.2018 `[И-3]` | Факт нормы подтверждён выдачей; **шкалу ставок не нашли**. Один источник (Гарант, фрагмент) называет «5 % при цене перепродажи до 100 тыс. ₽ включительно» и верхнюю ступень «305,5 тыс. ₽ + 0,25 % с суммы свыше 17 500 тыс. ₽», промежуточные ступени не видны `[И-3][Н]` — **использовать для расчётов нельзя до сверки с приложением**. Кому и как перечислять (в выдаче упомянута организация по коллективному управлению, УПРАВИС, в контексте 5% по старой редакции `[И-3]`) — `[Н][Ю]` |

Для продукта: поле «право следования применимо?» в лоте (автор жив/срок охраны, оригинал, не первая продажа), расчёт отчислений в протоколе, отчёт в организацию-получатель, учёт в Правилах (кто платит — продавец; сверить с договором) `[Ю]`.

|---|---|---|

**AI-подсказка цены (на базе проекта).** Что есть: каталог `ai-ml-service/` с маршрутами `admin`, `health`, `images`, `pdfs`, `rag` (`ai-ml-service/src/api/routes`) и схемой `src/database/ai_ml_schema.sql`; в деплой не включён (`CLAUDE.md`); в основном проекте — демо-режим без `AI_CORE_URL` (`src/routes/ai.ts:4`). Специального модуля оценки цен там нет (поиск по `price|estimate|valuation` дал только упоминания в `images.js`, `pdfs.js`, `admin.js`, `ai_ml_schema.sql`, не как функцию оценки — детально не изучали `[Н]`).

Предлагаемая последовательность:

1. **Не обещать «оценку», а давать «ориентировочную вилку с обоснованием»** для куратора, а не для публики. Автоматическая оценка без человека — риск вводящей в заблуждение информации и конфликта интересов.
2. **Слой данных:** таблица проданных лотов (автор, техника, размеры, год, дата, молоток, источник, лицензия на данные). Начать с собственного ручного ввода и разрешённых открытых источников.
3. **Базовая модель:** гедоническая регрессия по автору/размеру/технике/году с логарифмом цены; ближайшие аналоги (k-NN по эмбеддингам изображений и тексту — на базе Qdrant из `ai-ml-service`); вилка = квантили аналогов с поправкой на индекс.
4. **RAG-слой:** объяснение «почему такая вилка» с ссылками на конкретные продажи; обязательно показывать источники.
5. **Ограничения:** мало данных по современным российским авторам (выдача: рынок тонкий `[И-12]`); нужна пометка «недостаточно данных»; оценивание по картинке не заменяет эксперта.
6. **Правовая обвязка:** дисклеймер, отсутствие гарантий, учёт данных об авторах (ПДн), лицензии на базы `[Ю]`.

Трудоёмкость: прототип вилки по собственным данным — M; полноценная модель с ингестом внешних данных — L; зависит от доступа к данным (вопрос 10).
