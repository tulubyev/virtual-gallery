# Галерея и система залов

## Модель (единственный источник правды)

Живая модель — JSON в таблице `gallery_configs` (`GET/POST /api/gallery/config`). Описание и проверка — в
`src/frontend/src/lib/gallery/roomSpec.ts` (без React/three; её же использует сервер).

```
GalleryConfig { rooms: RoomSpec[], currentRoom }
RoomSpec {
  id, name,
  theme: classic | modern | minimal | dark,
  width, depth (3–50 м), height (3–15 м), wallColor (#rrggbb), lighting (0–100, штатно 70),
  slots,                         // сколько мест занято в раскладке
  connections: string[],         // двери в другие залы (до 6)
  artworkAssignments: { slot_1…slot_N: { id, title, artist, image_url, … } | null }
}
```

`normalizeConfig` вызывается и при сохранении (`POST` → 400 на мусор, мелкие ошибки исправляются и
возвращаются в `warnings`), и при чтении (старые записи в базе приводятся к модели), и в браузере.
Ссылки на картинки — только `/путь` или `http(s)://`, без `javascript:`/`data:`.

## Размеры зала → раскладка

`roomLayout(spec)` считает по реальным размерам:

- размер картин (`artSize`): от высоты зала, не больше 70 % меньшей стороны;
- места на стенах: сначала нижний ряд всех стен (задняя → левая → правая → передняя), затем верхний,
  если помещается по высоте; на передней стене остаются проёмы под двери;
- **вместимость** = число мест; редактор куратора не даёт занять больше (`roomCapacity`), при уменьшении
  размеров лишние места убираются;
- границы перемещения камеры, двери (`x`, ширина, высота), высота глаз.

Примеры: 3×3 — 2–3 места, 8×40 («кишка») — десятки, 50×50 — до `LIMITS.maxSlots` (120).

## Система залов

Залы связаны дверями (`connections`) — двери рисуются на передней стене с подписью названия зала.
Подошли к проёму — `onNavigate(toId)`: страница переключает зал и запоминает, откуда пришли
(`arrivedFrom`); посетитель появляется у двери, ведущей обратно (`spawnPoint`). В тесных залах точка
появления сдвинута от порога, иначе дверь сработала бы сразу. Список залов слева (сверху на телефоне)
позволяет перейти напрямую. Сцена пересоздаётся по ключу зала — текстуры прежнего зала освобождаются.

Тема (`THEME_STYLE`) задаёт материалы и характер освещения; `lightingPlan` переводит `lighting`, высоту,
площадь и цвет стен в физические интенсивности (общий свет + споты над картинами).

## Картинки и CDN

- Клиент просит картинку нужного уровня: 256 → 1024 → 2048 px (`textureSource`).
- Сервер отдаёт уменьшенные WebP по `/media/t/<ширина>/<u|s>/<файл|ключ S3>` (`src/services/media.ts`):
  `u` — каталог `public/uploads`, `s` — объект бакета S3; кэш на диске, неизменяемые заголовки.
- `CDN_BASE_URL` (например `https://cdn.virtgal.ru`) — адрес прокси-кэша: сервис `cdn` в
  `docker-compose.prod.yml` (nginx `proxy_cache`, конфиг `docker/cdn/nginx.conf`) ходит на приложение
  и кэширует ответы `/media/*`. Клиент узнаёт адрес из `GET /api/public-config`; пусто — всё идёт с основного
  сервера. Исходные изображения из S3 тоже читаются через `/media/.../s/…`, поэтому адрес бакета браузер не
  видит и ему не нужен CORS.

## Куда развивать

- Планировки сложнее прямоугольника (L-образные залы, колонны, перегородки): `roomLayout` уже отделён от
  рендера — достаточно вернуть другой набор мест/стен.
- Связь с реляционными таблицами `galleries`/`rooms` (в схеме есть, но не используются): пока источник —
  JSON; миграция имеет смысл, когда понадобятся несколько галерей и права по залам.
